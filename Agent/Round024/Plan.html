一、现状调查结论（核心发现）

发现 1：当前 build/SwComForTool.app 不能在别的 Mac 上运行

直接原因：二进制 LC_RPATH 指向开发机绝对路径 /Users/swnw/Documents/Software/SwComForTool/Qt/6.8.3/macos/lib，且 bundle 内 没有 Frameworks/、没有 PlugIns/、没有 qt.conf。换台没装 Qt 的 Mac 启动会立即 dyld 报错 Library not loaded: QtWidgets.framework。

这不是 macdeployqt 的问题——build/ 是原始编译产物，从未经过 deploy。要让包可独立运行，必须跑 macdeployqt 把 Qt 框架/插件拷进 bundle 并改写 rpath。

发现 2：本机已有一个"能跑"的可移植模板，可直接对照

issue/ComforToolV1.1_macOS.zip（旧版产物）拆开是完全自包含的：rpath=@executable_path/../Frameworks、Frameworks 含 Qt6 全家桶、PlugIns 含 cocoa/styles/imageformats、有 qt.conf、minos 13.0、SDK 15.4。deploy/ComforTool.app（7-19）同样是自包含的。证明本机 macdeployqt 完全可用，只是当前 pack.sh 从未在 Mac 上真正跑过（见 Round023 遗留）。本次按此模板产出即可。

二、方案设计

2.1 核心思路

本轮 不改任何功能源码，全部工作集中在构建/打包链路，把"原始编译产物"变成"可独立运行的自包含 bundle"，并落到 issue/Mac_Arm64/。流程：

cmake  ──▶  build/SwComForTool.app (rpath=绝对路径, 不可移植)
   │
   └─ pack.sh ──▶ macdeployqt 改 rpath=@executable_path/../Frameworks + 拷 Qt 框架/插件 + qt.conf
                 + adhoc 重新签名整个 bundle
                 ──▶ deploy/SwComForTool.app (自包含, 可移植) ★
                        │
                        ├─▶ 复制到 issue/Mac_Arm64/ (展开目录, D2) ★
                        └─▶ 打 issue/SwComForToolV1.0.0_macOS.zip (分发用)

对照"发现 2"的旧可移植模板结构逐项核对，确保产出与之等价。

版本 d 追加 — 首帧 HID 写入 BadArgument 超时修复

触发：用户实机测试反馈"打开软件发送的第一帧都超时，重发才成功"。

根因：IOHIDDeviceSetReport 打开后首次写入返回 kIOReturnBadArgument(0xE00002C2)（IOHIDInterface 未就绪 transient），包未发出→3s 超时；重发即成功（升级路径重试已自愈、用户手动重发亦成功）。手动握手只发 1 次→中招；升级有重试→自愈。

修复：HidManagerMac::writeData 内对 BadArgument/NotReady/Offline 重试 SetReport（30×30ms=900ms，<3s 响应超时），成功即跳出。覆盖所有写入路径；不动 writeData 签名、不动 HidManagerWin（#ifdef Q_OS_MACOS 守护）→ D1 满足、Win 零影响。dev 机 attempt 0 即 rc=0 零开销。

验证：dev 机实跑（AX 驱动握手）attempts=1 rc=0+2 响应+0 BadArgument（无回归）；重试路径 dev 机不触发，由历史日志+用户重发证明。用户侧用新包重测确认首帧不再超时。

改动：仅 src/HidManagerMac.cpp（writeData 重试 + #include <QThread>）。已执行并更新 Report.html 第九节。

计划要点：不改功能源码 → 不影响跨平台接口（D1✓）；重写 pack.sh 跑 macdeployqt 产出自包含 bundle 并复制到 issue/Mac_Arm64/（D2✓）；据 minos/SDK 数据给出 macOS 14/15/26 兼容结论（D3✓，26 为推断）。版本 d：修复首帧 BadArgument 超时（已执行）。
