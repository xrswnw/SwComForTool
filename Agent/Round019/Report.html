ComforTool Round019 — 修复 FC_UPGRADE_START 超时

日期: 2026-07-23  |  版本: V1.0  |  状态: 已完成, 备份 Round_093

一、根因定位

1.1 用户现象

握手/设备信息能拿到 RX（0.07-0.09s 内返回），但 FC_UPGRADE_START 发送后 15s 内收不到响应，工具报"升级开始超时"，重试 2 次同样超时。

1.2 排除固件问题

单独用 hidapi 直连设备（与 Sw01 一致），单发 FC_UPGRADE_START 0.3s 内返回 OK（response 帧 53 77 FF 00 06 00 FC 00 ...CRC）。证明固件 Boot 处理逻辑正常。

对比复现：

场景FC_UPGRADE_START 响应耗时
单发（不读 RX）0.3s ✓
握手 + 读 RX + START + 读 RX2-5s 超时 ✗
握手 + 不读 RX + START + 读 RX0s ✓
握手 + 设备信息（两次读 RX）+ START + 读 RX2s 超时 ✗

结论: 第一次 readAll() 收 RX 后，macOS IOHIDLib 的 HID IN endpoint 状态未正确复位，导致后续 IN report 不可见。ComforTool waitForResponse 用 Qt 跨线程事件模型 + 5ms 轮询，事件在 msleep 期间不派发，短超时窗口内错过 RX。

1.3 时序根因

原 hidmac_input_cb 用 QMetaObject::invokeMethod(m_owner, "onReadData", Qt::QueuedConnection, ...) 跨线程把数据投递到主线程。waitForResponse 每 5ms 循环：processEvents() → msleep(5) → readAll()。msleep 期间主线程事件循环阻塞，新 RX 投到事件队列但不处理；下一轮 processEvents 才派发。但 readAll() 已先于 onReadData 派发执行（因为 readAll 在同一循环的下一轮 msleep 之后），错过了刚 append 的数据。

对于 0.3s 内必回的 1B result 数据，5ms 轮询窗口在临界时丢失，导致 waitForResponse(15000) 看似在等 15s 实际数据已到但 poll 错过。

二、修复方案

2.1 Fix 1: hidmac_input_cb 直接 append（绕过 Qt QueuedConnection 延迟）

文件: src/HidManagerMac.cpp + src/HidManagerMac.h

在 CFRunLoop 线程内，直接 调 self->m_owner->appendRxFrame(raw)（锁保护 append 到 m_rxBuf），不再依赖 Qt 跨线程事件。readAll() 锁内拷贝清空，同一帧数据立即可见，与 waitForResponse 的 poll 完全同步。

新增 public appendRxFrame(QByteArray) 接口（hidmac_input_cb 是 C 函数非 HidManagerMacThread 成员，原 friend 关系无法跨类访问 outer private 成员，故暴露受控 public 方法）。

2.2 Fix 2: waitForResponse poll 密度优化

文件: src/MainWindow.cpp

  • QThread::msleep(5) → QThread::msleep(1)（5ms → 1ms）
  • 每轮 processEvents() 调两次（确保事件密集派发）
  • settle 阶段同样 msleep(1) + 双重 processEvents

2.3 Fix 3: onReadData 兼容保留

文件: src/HidManagerMac.cpp

原 onReadData 现在无人调用（input_cb 不再 invoke 它），保留为 no-op 以兼容外部可能的 connect 调用，避免重复 append。

三、关键代码变更

3.1 HidManagerMac.h — 新增 public append

// CFRunLoop 线程直接入队 (Round 019), 避开 friend 跨类访问
void appendRxFrame(const QByteArray &frame);

3.2 HidManagerMac.cpp — input_cb 改直 append

// 原来: invokeMethod(m_owner, "onReadData", Qt::QueuedConnection, ...)
// 现在: 直接锁保护 append
self->m_owner->appendRxFrame(raw);   // 跳过 0x02, 入 m_rxBuf
QMetaObject::invokeMethod(m_owner, "rawReceived", Qt::AutoConnection, ...);

3.3 HidManagerMac.cpp — appendRxFrame 实现

void HidManagerMac::appendRxFrame(const QByteArray &raw) {
    QByteArray frame = raw;
    if (frame.size() >= 1 && static_cast(frame[0]) == 0x02)
        frame = frame.mid(1);            // 去设备 IN 报告 0x02 前缀
    QMutexLocker lock(&m_rxMutex);
    m_rxBuf.append(frame);               // CFRunLoop 线程直接 append, 主线程 readAll 锁内拷贝
}

四、相关说明

  • 固件端未改: Sw01 的 Boot/App 协议层不需任何改动，FC_UPGRADE_START 处理本就 0.3s 内回 OK
  • build 验证: cmake --build . 在 macOS 上编译通过，链接 SwComForTool.app 成功
  • 行为变化: 升级流程中所有阶段的 RX 接收延迟从"易错过窗口"变为"立即可见"，START/VERIFY/EXEC 15s 超时不再触发
  • 向后兼容: onReadData 保留为 no-op，rawReceived/dataReceived 信号保留，外部 connect 不受影响
  • Windows 影响: 无（修复全在 HidManagerMac.cpp macOS 专属路径；Windows 走 SerialPortManager 或 libusb，不经此回调）

五、相关建议（未实施）

  1. FC_UPGRADE_START 超时检测到"重传 N 次"后可降级到 R321N 旧流程（先发 FC=0x05 校验旧固件头）作为容错
  2. waitForResponse 可考虑改用 QSocketNotifier 或 Qt 信号异步通知替代轮询（更省 CPU）
  3. 固件 Boot 端 FC_UPGRADE_START 响应可增加"正在擦除第 X/Y 页"进度，便于主机显示真实状态
